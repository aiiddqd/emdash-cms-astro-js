# RFC: MCP-сервер EmDash для управления контентом

## Вводные

EmDash автоматически подключает MCP endpoint `/_emdash/api/mcp`; сообщение при `pnpm dev` лишь сообщает его адрес, а не запускает отдельный процесс. В текущем `astro.config.mjs` опция `mcp` не задана, поэтому endpoint включён по умолчанию. Он даёт внешнему AI-клиенту стандартизированные операции с CMS, а не доступ к исходному коду или документации EmDash.

Рекомендуется оставить MCP включённым для локального исследования и будущего редакционного сценария, но не подключать production-клиентов и не выпускать широкие токены, пока не определены владелец, AI-клиент и требуемые разрешения. Для deployment за reverse proxy обязательна корректная публичная origin-конфигурация через `siteUrl` или `EMDASH_SITE_URL`.

## Назначение и цели

Цель — зафиксировать безопасный и воспроизводимый способ включать встроенный MCP-сервер EmDash на уровне этого Astro-проекта.

Решение должно:

- позволять редактору подключить совместимый MCP-клиент и работать с `posts`, `pages`, таксономиями, меню, медиа и настройками сайта;
- применять принцип минимальных привилегий: отдельные ограниченные OAuth-grant или Personal Access Token (PAT) для каждого клиента/сценария;
- не путать site MCP с Docs MCP: `https://docs.emdashcms.com/mcp` только ищет документацию для coding-агента и не читает и не изменяет CMS;
- быть безопасным при переходе с `localhost` на публичный SSR deployment.

В RFC не входит разработка custom-плагина или публикация сайта. Проект также не должен передавать в MCP исходный код, секреты, SQLite-файл или медиа-хранилище напрямую: клиент получает только результаты разрешённых MCP-инструментов.

## Составляющие и особенности

### Текущее состояние

`astro.config.mjs` подключает `emdash()` с SQLite, локальным storage и audit-log. Так как `mcp` отсутствует, EmDash монтирует stateless Streamable HTTP endpoint на `/_emdash/api/mcp`. Это маршрут единого Astro/Node-приложения, а не отдельный dev server. `POST` принимает JSON-RPC вызовы; соединения и SSE-сессии не поддерживаются.

Локальная проверка 2026-08-28: неаутентифицированный запрос к `http://localhost:4321/_emdash/api/mcp` получил `401 NOT_AUTHENTICATED` и `WWW-Authenticate` с OAuth protected-resource metadata. Endpoint не раскрывает контент анонимному посетителю.

### Управление на уровне проекта

Единственный переключатель core MCP — опция интеграции EmDash:

```ts
emdash({
  // Явное включение допустимо для читаемости; это и так значение по умолчанию.
  mcp: true,
  // siteUrl: "https://cms.example.com", // только публичный production origin
})
```

`mcp: false` отключает инъекцию маршрута. Его следует задавать в окружениях, где AI-доступ к CMS не нужен. Не следует включать/выключать маршрут через код страниц Astro или веб-серверные rewrite-правила.

Для production за TLS-terminating proxy задать `siteUrl` или переменную `EMDASH_SITE_URL` как точный публичный origin без path. Это необходимо для OAuth redirects и MCP discovery: внутренний `http://localhost:4321` не должен попадать в metadata, которые видит MCP-клиент. Одновременно настроить `astro.config.mjs` `site`, если публичные шаблоны строят canonical/OG URL через Astro; эти настройки решают разные задачи.

Конфигурации `.mcp.json`, `.cursor/mcp.json` и `.vscode/mcp.json` из шаблона относятся к **Docs MCP**. Они не включают и не конфигурируют endpoint текущего сайта. Конфигурацию site MCP добавляет каждый пользователь в выбранный клиент с URL вида `https://<public-origin>/_emdash/api/mcp`; секреты и PAT в Git не коммитятся.

### Доступ и разрешения

Клиент проходит OAuth 2.1 Authorization Code + PKCE либо использует созданный в админке PAT. Каждому клиенту выдаётся самостоятельный grant с минимальными scopes:

| Сценарий | Разрешения |
| --- | --- |
| Поиск, чтение постов/страниц/таксономий/меню | `content:read` |
| Черновик и редактирование контента | `content:read`, `content:write` |
| Работа с медиатекой | `media:read` и, только при необходимости, `media:write` |
| Чтение/изменение настроек | `settings:read` / `settings:manage` |
| Изменение схемы | `schema:read` / `schema:write`; только для администратора и не для обычного редакционного агента |

`admin` и `schema:write` не использовать для ежедневного AI-копирайтинга. Операции публикации, удаления, восстановления ревизий и изменения меню должны выполняться только по явному запросу человека в диалоге клиента. Передавать токен облачному AI-сервису допустимо только после отдельного решения владельца сайта: результат MCP-вызова и доступный контент могут обрабатываться этим сервисом.

### Плагины и custom-инструменты

Сейчас `@emdash-cms/plugin-audit-log` не объявляет MCP tools, поэтому дополнительных действий нет. В будущем плагин может экспонировать только явно перечисленные private routes с Zod input schema, permission и `destructive` flag. После ревью администратор отдельно включает инструменты плагина в EmDash Admin; клиенту также нужен `mcp:tools` или `mcp:tools:<pluginId>`. Нельзя считать любой API route плагина MCP-инструментом автоматически.

## Критерии приемки (checklist)

- [ ] В README или в production runbook явно различены Docs MCP и MCP данного сайта, указан только шаблон URL без токенов.
- [ ] В выбранном окружении решение о `mcp: true` (явно или по умолчанию) либо `mcp: false` зафиксировано в `astro.config.mjs` и проверено после перезапуска.
- [ ] Неаутентифицированный запрос к включённому endpoint возвращает `401` с OAuth discovery header и не содержит CMS-данных.
- [ ] Для публичного deployment `siteUrl` или `EMDASH_SITE_URL` указывает на реальный HTTPS origin; protected-resource metadata и OAuth redirect используют именно его.
- [ ] Тестовый read-only клиент с `content:read` способен выполнить `tools/list` и чтение `posts`, но получает `INSUFFICIENT_SCOPE` при попытке записать контент.
- [ ] Для каждого write-клиента задокументированы владелец, назначение, scopes, дата создания и процедура отзыва; значения токенов нигде не хранятся в репозитории.
- [ ] Перед включением MCP tools любого плагина администратор проверяет его permissions, input/output schemas и destructive-флаги; для audit-log дополнительных инструментов не включено.

## Дорожная карта

1. Утвердить, нужен ли MCP только локально, в production или пока следует отключить его вне разработки.
2. Выбрать первого владельца и клиент для теста; создать отдельный read-only OAuth grant/PAT с `content:read`.
3. Подключить клиент по локальному URL, выполнить read-only smoke test и отозвать тестовый токен.
4. При подготовке production задать публичный origin, HTTPS и persistent storage согласно deployment RFC; повторить OAuth discovery test через публичный домен.
5. Только после успешного read-only этапа создать отдельный write grant для согласованного сценария создания черновиков. Публикацию и схему оставить вне его scopes.
6. При появлении плагинов с MCP tools проводить отдельный security review и фиксировать решение отдельным дополнением к RFC.

## Варианты решений

### Вариант A: оставить MCP включённым по умолчанию

Подходит для локальных экспериментов и последующего редакционного workflow. Endpoint уже требует токен, а доступ ограничивается ролями и scopes. Минус — необходимо поддерживать дисциплину выпуска и отзыва токенов.

### Вариант B: `mcp: false` до появления подтверждённого сценария

Минимизирует поверхность API на раннем MVP. Минус — для каждого теста AI-редактирования потребуется изменение конфигурации и перезапуск.

### Рекомендация по выбору

Выбрать вариант A в local development, не создавая токенов без конкретного теста. Для будущего production принять отдельное решение в deployment RFC: включать только при назначенном владельце и настроенном публичном origin; в противном случае использовать вариант B.

## Открытые вопросы

- Какой внешний MCP-клиент и модель будут первыми потребителями site MCP, и допускает ли политика проекта передачу им редакционного контента?
- Нужна ли production-автоматизация черновиков, или MCP останется инструментом локального редактора?
- Где будет храниться реестр выданных токенов и кто имеет право их отзывать?

## Итого и рекомендации

Строка `MCP server http://localhost:4321/_emdash/api/mcp` — ожидаемый вывод EmDash 0.35.0: встроенный, аутентифицированный API-интерфейс для AI-клиентов. Для данного репозитория базовая политика — отделить его от Docs MCP, ограничивать доступ scopes и не выпускать production credentials до определения владельца и public origin.
